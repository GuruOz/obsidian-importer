# Project Specification & Architectural Blueprint

This document serves as the absolute source of truth for the `obsidian-importer` project. Any LLM picking up this repository should read this document first to understand the system architecture, constraints, and filing logic.

## 1. System Overview
The goal of this project is to run a **fully automated, headless, nightly pipeline** that ingests daily Microsoft Copilot summary emails (digests), extracts the structured knowledge, and uses an autonomous LLM agent to logically file that knowledge into a local Obsidian vault (`Galaxy Brain`). 

The system runs completely unattended inside a Docker container (`obsidian-importer-pipeline`) using a chron scheduler (`supercronic`).

## 2. Key Components & File Structure
*   **`.env` / `docker-compose.yml`**: Defines the environment variables and container mounts. The pipeline container binds the local data directory to `/work` and an isolated Docker volume (`obsidian_only_vault`) to `/vault`. A standalone Obsidian container provides GUI access to this isolated vault via VNC (port 3000).
*   **`scripts/run-digest.sh`**: The main orchestrator script.
    *   Takes incremental `rsync` snapshots of the vault before any operations (for safety).
    *   Calls `fetch_digest.py` to retrieve the latest email and save it to `/work/staging/digest.md`.
    *   Generates a flat index of all existing markdown files in the vault and saves it to `/work/staging/vault_index.txt`.
    *   Invokes the LLM Agent (either Claude CLI or Custom Python Agent) to process the digest.
    *   On successful production runs (`DRY_RUN=0`), archives `digest.md` into `/vault/Raw Digests/Copilot Digest - <DATE>.md`.
*   **`scripts/custom_agent_loop.py`**: A custom, standalone Python tool-calling harness. It interfaces with any OpenAI-compatible API (e.g., DeepSeek, OpenRouter) via the `openai` SDK, exposing file-system tools so the LLM can explore the vault and write files.
*   **`prompt_template.txt` & `prompt_dry_run.txt`**: The system instructions fed to the LLM agent. These contain strict behavioral rules for how data should be interpreted and filed.

## 3. Agent Tooling Capabilities
When `AGENT_ENGINE=custom` is defined in `.env`, `custom_agent_loop.py` is invoked. It grants the LLM the following JSON-schema tools:
*   `read_file(path)`: Reads content of a specified file.
*   `glob_search(pattern)`: Searches for files matching a path pattern (e.g., `*Purview*.md`).
*   `grep_search(query)`: Performs regex searches inside the content of all markdown files.
*   `write_file(path, content)`: Creates a new file or overwrites an existing one. (Restricted to `proposed.md` during Dry Runs).
*   `edit_file(path, old_string, new_string)`: Performs precise string replacements on an existing file without having to rewrite the entire document.
*   `finish(status, work_date, files_touched, entries_filed, sections)`: **REQUIRED.** The agent must call this tool to yield control back to the orchestrator script with a structured JSON payload indicating completion.

## 4. Business Logic: The Filing Rules
To ensure the Obsidian vault remains useful and organized, the LLM agent is strictly bound to the following constraints (enforced via `prompt_template.txt`):

1.  **Lossless Preservation (No Summarization):** The agent MUST NOT summarize, compress, or omit any operational details. Technical parameters, exact error messages, pending action items, and names of individuals (e.g., "Sandeep Sheshappa") must be fully retained.
2.  **Aggressive Note Granularity:** Note titles must be highly specific to the distinct issue, task, or topic.
    *   **Rule:** The agent MUST NEVER lump specific scenarios, tests, or incidents into generic umbrella notes. 
    *   **Example:** If testing a specific RNS policy tip, the agent must CREATE a new note `Work/CDLP/Testing/Purview/RNS global policy tip testing.md`, and MUST NOT append to a generic `Purview policy tips limitation.md`.
3.  **Idempotency & Context Awareness:** The agent uses `vault_index.txt` to check for existing notes. It should intelligently decide to update a highly-specific existing note if the context matches exactly, otherwise, it defaults to creating a new specific note.
4.  **Global Linking:** The agent should proactively introduce Obsidian wikilinks (`[[Concept Name]]`) to connect related entities globally across the vault (e.g., linking a support ticket to an architectural design note).
5.  **Unambiguous Dates:** All dates generated by the agent must use the unambiguous format `YYYY-MM-DD (MMM)` (e.g., `2026-07-03 (Jul)`) to ensure automated chronological sorting in Obsidian while avoiding DD/MM vs MM/DD confusion.

## 5. Deployment Lifecycle
Because the Dockerfile uses `COPY scripts/ ./scripts/`, any modifications made to the shell or python scripts on the host machine **will not take effect** in the running container until the image is rebuilt. 
*   **To apply script changes:** Run `docker compose build pipeline` followed by `docker compose up -d pipeline`.
*   **Dry Run Mode (`DRY_RUN=1`):** The agent operates normally but its write permissions are restricted. It can only output its final proposed markdown structure to `data/staging/proposed.md`. The vault is untouched.
*   **Production Mode (`DRY_RUN=0`):** The agent writes directly to the vault. The orchestrator handles backups and archives the raw digest.
